# Mini Git 핵심 질문 및 답변 요점

이 문서는 질문을 읽고 **정의 → 동작 순서 → 실제 코드 근거 → 선택 이유**로 설명하기 위한 자료입니다. 코드는 모두 `main.py`에 있습니다.

## 프로그램 구조·자료구조

### Q1. 프로그램은 어디서 시작하고 어떻게 끝나는가?

- **요점**: `if __name__ == "__main__"`에서 `main()`을 실행하고 `MiniGit` 객체를 하나 만듭니다. `input("mini-git> ")` → `execute()` → 결과 출력이 반복됩니다.
- **종료**: `EXIT`/`QUIT`를 인자 없이 입력하면 `execute()`가 `None`을 반환합니다. EOF나 Ctrl+C도 종료합니다.
- **코드**: `main()`, `MiniGit.execute()`.

### Q2. 공백 포함 메시지와 대소문자를 어떻게 처리하는가?

- **요점**: `shlex.split()`이 따옴표 안의 공백을 하나의 인자로 보존합니다. `command.upper()`로 명령의 대소문자를 무시합니다.
- **오류**: 인자 개수가 틀리거나 따옴표가 닫히지 않으면 `Invalid args`를 반환합니다.
- **코드**: `MiniGit.execute()` 시작 부분 및 각 명령 분기.

### Q3. hash, branch, HEAD는 어떤 관계인가?

- **요점**: `commits[hash]`는 커밋 객체를 찾는 사전이고, `branches[branch_name]`은 해당 브랜치의 마지막 커밋 hash입니다. `current_branch`가 현재 선택된 브랜치 이름입니다.
- **예시**: `BRANCH feature`는 HEAD의 hash를 복사하고, `SWITCH feature`는 현재 브랜치 이름만 바꿉니다.
- **코드**: `MiniGit.__init__()`, `initialize()`, `execute()`의 `BRANCH`/`SWITCH`.

### Q4. 커밋에는 어떤 정보가 저장되는가?

- **요점**: `Commit`은 `hash`, `message`, `author`, `timestamp`, `parents`를 저장합니다. `@dataclass(frozen=True)`로 생성된 커밋의 필드 변경을 막습니다.
- **코드**: `Commit`, `MiniGit.create_commit()`.

### Q5. 왜 커밋 그래프는 DAG인가?

- **정의**: 방향성과 사이클이 없는 그래프입니다. `parents` 간선은 자식에서 부모로 향합니다.
- **논리**: 새 커밋은 과거에 이미 존재하는 커밋만 부모로 연결합니다. 따라서 새 노드에서 시작해 다시 자기 자신으로 돌아오는 경로가 생기지 않습니다.
- **코드**: `MiniGit.create_commit()`의 `parent` 및 `parents` 생성.

### Q6. 커밋의 hash는 실제 Git처럼 SHA인가?

- **답**: 아닙니다. `next_number`를 증가시키고 16진수 8자리 이상으로 표시한 식별자입니다. 파일 내용이 없으므로 내용 해시가 필요하지 않습니다.
- **유일성**: `INIT` 재호출에도 카운터를 초기화하지 않아 같은 실행 중 값이 재사용되지 않습니다.
- **코드**: `MiniGit.initialize()`, `create_commit()`.

### Q7. `INIT`을 다시 실행하면 어떻게 되는가?

- **요점**: 커밋·브랜치·두 인덱스가 초기화되고 `main` 브랜치와 작성자가 설정됩니다. 이전 커밋에 접근할 수 없습니다.
- **코드**: `MiniGit.initialize()`.

## 탐색과 그래프 정렬

### Q8. 왜 일반 `LOG`는 단순 최신순이 아닌가?

- **요점**: 부모가 자식보다 먼저 출력돼야 하기 때문입니다. 생성 시각으로 정렬하는 것과는 다른 **부분 순서 제약**입니다.
- **코드**: `topological_log()`, `MiniGit.execute()`의 `LOG`.

### Q9. 부모 우선 로그를 어떤 알고리즘으로 만드는가?

- **요점**: Kahn 위상 정렬. 부모 개수를 기록한 뒤 0인 노드부터 큐에서 꺼내고, 해당 부모가 처리될 때 자식의 미처리 부모 수를 감소시킵니다.
- **복잡도**: O(V + E), V는 커밋 개수, E는 부모 연결 개수입니다.
- **코드**: `topological_log()`.

### Q10. `PATH`는 왜 BFS를 사용하는가?

- **요점**: 모든 간선의 비용이 1이므로 BFS는 거리(간선 수) 0, 1, 2… 순으로 탐색합니다. 최초 방문 경로가 최단입니다.
- **방향**: 자식·부모 연결을 양방향으로 만들어 탐색합니다. 목표에 이르지 못하면 `No path`입니다.
- **코드**: `shortest_path()`.

### Q11. 최단 경로가 여러 개면 어떻게 선택하는가?

- **요점**: 인접 hash를 직접 만든 `merge_sort`로 사전순 정리한 뒤 BFS에 넣습니다. 같은 길이라면 더 앞선 경로가 먼저 발견됩니다.
- **주의**: CLI에는 `MERGE`가 없어서 일반 사용 시 하나의 커밋이 가지는 부모는 최대 1개입니다. 다중 부모 DAG에서의 동률은 단위 테스트의 인위적 그래프로 확인합니다.
- **코드**: `shortest_path()`, `tests/test_main.py`의 `test_path_lexicographic_tie_break_with_multiple_parents`.

### Q12. `ANCESTORS`는 어떻게 모든 조상을 찾는가?

- **요점**: 부모를 스택에 넣고 DFS로 따라갑니다. 방문한 hash는 `found` 집합에 넣어 중복 탐색을 막습니다. 대상 자신은 반환하지 않습니다.
- **복잡도**: 탐색하는 조상 부분 그래프의 노드 Va, 간선 Ea에 대해 O(Va + Ea).
- **코드**: `find_ancestors()`.

### Q13. 스택과 큐의 차이는 무엇인가?

- **큐(FIFO)**: 먼저 넣은 노드부터 꺼내는 구조. BFS와 위상 정렬의 `deque.popleft()`에 사용됩니다.
- **스택(LIFO)**: 마지막에 넣은 노드부터 꺼내는 구조. DFS의 `list.pop()`에 사용됩니다.
- **코드**: `shortest_path()`, `topological_log()`, `find_ancestors()`.

## 역색인과 정렬

### Q14. 역색인은 무엇이고 왜 빠른가?

- **요점**: 메시지 단어·작성자를 각각 해당 커밋 hash의 집합에 연결한 사전입니다. 전체 N개를 매번 훑지 않고 해당 키의 후보 K개를 조회합니다.
- **대가**: 커밋을 생성할 때 인덱스 갱신과 추가 메모리가 필요합니다.
- **코드**: `MiniGit.create_commit()`, `search_keyword()`, `execute()`의 `SEARCH`.

### Q15. 키워드 토큰은 어떻게 생성하며 중복을 어떻게 제거하는가?

- **요점**: `message.lower().split()`으로 공백 단위·소문자 토큰을 만들고 `set(...)`으로 한 메시지 내 중복 단어를 제거합니다.
- **예**: `"Login login"`을 저장하면 `login`의 게시 목록에 해당 커밋 hash가 한 번만 들어갑니다.
- **코드**: `MiniGit.create_commit()`.

### Q16. 여러 단어 검색은 전체 커밋을 검사하는가?

- **답**: 아닙니다. 각 단어의 hash 집합을 교집합으로 좁힌 뒤 **후보 커밋만** 검사해 구절 순서가 맞는지 확인합니다.
- **복잡도**: 조회·집합 연산·후보 메시지 확인·결과 정렬 비용에 따라 달라지며, 전체 N개 커밋을 항상 훑는 방식은 아닙니다.
- **코드**: `MiniGit.search_keyword()`.

### Q17. 사용한 정렬 알고리즘과 평균·최악 시간복잡도는?

- **답**: 직접 구현한 병합 정렬. 평균 및 최악 모두 O(n log n), 추가 공간 O(n)입니다.
- **이유**: 절반으로 분할하고 정렬된 두 부분을 선형 시간에 병합하므로 한 단계마다 O(n), 깊이는 O(log n)입니다.
- **코드**: `merge_sort()`.

### Q18. 안정 정렬이란 무엇이며 이 구현은 안정적인가?

- **정의**: 비교 키가 같은 두 원소의 상대 순서를 유지하는 정렬입니다.
- **근거**: 병합할 때 `key(left[i]) <= key(right[j])`이면 **왼쪽 항목**을 먼저 선택합니다. 따라서 안정 정렬입니다.
- **코드**: `merge_sort()`.

### Q19. 날짜·작성자 정렬은 어떻게 분리되는가?

- **요점**: 동일한 병합 정렬 함수에 다른 `key`를 전달합니다. 날짜는 UTC ISO 시각 문자열, 작성자는 이름 소문자입니다.
- **주의**: 명령만 사용하는 일반 저장소는 `INIT`에 설정한 한 명의 작성자를 가지므로 작성자 정렬은 동률이 많습니다. 구현 함수가 여러 작성자를 처리하는지는 단위 테스트에서 별도로 검증합니다.
- **코드**: `MiniGit.execute()`의 `LOG --sort-by=...`, `merge_sort()`.

### Q20. 왜 Python의 `sorted()`를 사용하지 않았는가?

- **요점**: 정렬 과정의 분할·비교·병합을 직접 이해하고 설명해야 하기 때문입니다. 표준 정렬 API 대신 병합 정렬을 구현했습니다.
- **코드**: `merge_sort()` 및 검색·경로·로그 호출부.

## 설계와 검증

### Q21. 파일을 실제로 저장하거나 변경 이력을 비교하는가?

- **답**: 아닙니다. 메모리의 커밋 메타데이터와 브랜치 포인터만 관리합니다. 파일 스냅샷·네트워크·영속성은 구현하지 않습니다.
- **코드**: `MiniGit.__init__()`의 사전 상태, `Commit` 데이터 구조.

### Q22. 어떤 예외·경계 조건을 검증했는가?

- **요점**: 초기화 전 명령, 따옴표 오류, 잘못된 인자, 미존재 브랜치/커밋, 중복 브랜치, 비어 있는 로그, 독립 그래프의 `No path`, 첫 커밋의 조상 없음, 재초기화, 멀티 부모 동률 경로, 긴 조상 체인, 반복 검색 및 실제 REPL 종료.
- **실행**: `python -m unittest discover -s tests -v`.
- **코드**: `tests/test_main.py`.

## 설명을 준비할 때의 핵심 구분

1. **Git vs Mini Git**: 실제 Git처럼 파일을 저장하는 시스템이 아니라 *커밋 그래프 학습용 모델*입니다.
2. **LOG vs 정렬 로그**: 기본 `LOG`는 위상 순서, `--sort-by`는 단일 비교 키에 따른 정렬입니다.
3. **DFS vs BFS**: DFS는 모든 조상을 탐색, BFS는 간선 수가 가장 적은 경로를 찾습니다.
4. **해시맵 vs 역색인**: 해시맵 `commits[hash]`는 단일 커밋 조회, 역색인 `keyword/author → hash 집합`은 조건 검색입니다.
5. **명령어 지원 vs 자료구조 가능성**: `MERGE` 명령은 구현하지 않았지만 그래프 알고리즘은 여러 부모를 처리합니다.
